DAT dApp Architecture Principles (Provisional)

Positioning

This document describes the pre-deployment architecture for DAT.
It is a provisional, unaudited, and undeployed design.
No official DAT smart contract has been deployed.

Base Architecture

As with the CAWELON and EMA designs, the DAT base token is separated from
dApp-specific protocol contracts.

1. DAT Base Token

- OP Mainnet ERC-20
- Fixed initial supply of 1,000,000,000 DAT
- 0% transfer / buy / sell tax
- No rewards or reflection
- No additional minting
- Self-burn only
- EIP-2612 Permit support
- No owner, administrator, pause, upgrade, or proxy authority

2. dApp Protocol Contracts

- Connect to DAT through IERC20
- Use OpenZeppelin SafeERC20 for token transfers
- Use IERC20Permit for signature-based approvals when Permit is enabled
- Place dApp-specific functions, restrictions, and update procedures in this layer
- Keep liquidity-state-transition logic separate from the base token
- Define every state transition through explicit, reviewable rules

3. Frontend

- Support wallets compatible with OP Mainnet
- Display DAT balances
- Support Permit signatures or standard approvals
- Interact with the relevant dApp protocol contracts
- Clearly disclose source code, audit status, and deployment addresses on GitHub

Reasons for Separation

- New dApps can be added without reissuing the DAT base token
- A 0% tax and no-reflection design prevents unexpected balance changes
- The attack surface of the base token remains small
- Audit, pause, and upgrade policies can be designed independently for each dApp
- Standard compatibility with wallets, DEXs, and OP Mainnet explorers is easier to preserve

Items to Confirm Before Deployment

- Wallet receiving the initial supply
- Distribution, liquidity, and allocation rules
- Whether any fixed restrictions belong in the base token or the dApp layer
- Whether ERC20Votes is required for on-chain voting or delegation
- Independent security audit procedures
- OP Sepolia testing procedures
- Public disclosures reflecting future USPTO developments

Not Adopted in the Base Token

- dApp-specific logic embedded in the token contract
- Transfer, buy, or sell taxes
- Automatic holder rewards
- Reflection
- DEX-pair detection
- Automatic distribution to a marketing wallet
- Post-deployment minting
